# 従業員用「所属店舗のシフト表だけ」閲覧 — 非公開の設計・検証

## 2026-11-15 仕様更新
- **従業員番号とパスワードによるログイン案を撤回する。**
- **「自分のシフト」ページを作らない。**
- 従業員には **所属店舗の確定済みシフト表全体** だけを表示する。個人別一覧、勤務希望、従業員検索、従業員台帳、編集・削除画面、他店舗への切替は実装しない。
- 管理者用の既存ページは従業員に渡さない。専用サイトは **必ず別オリジン** に配置する。管理者のGitHub Pagesと同じ `*.github.io` オリジンのサブフォルダには置かない。
- **従業員用画面では「確定」「未確定」を一切表示しない。** 状態ラベル、色分け、ステータスメッセージ、確認アイコンを付けない。管理者側の確定判定は、従業員に配信する週を制御するためだけに使用する。
- 閲覧できる週は、**既存シフト表をそのまま**表示する。前週・今週・次週の切り替えは可能だが、まだ公開されていない週は「この週のシフト表は表示できません」とだけ案内する（理由や確定状態を伝えない）。
- シフト表そのもののレイアウト、表示枠、時間帯、文字サイズを勝手に変更しない。従業員サイトでは管理者機能・自分のシフトページ・ステータス表示を追加しない。

## 重要な安全上の境界
1. 管理者の `shift_app_state` や `localStorage` のデータを従業員サイトから読む設計にしない。既存のクラウド同期データ `projectScheduleRoot()` も、`employeeId`・過去週などを含むため **そのまま渡さない**。
2. `projection.mjs` は **管理者側/信頼できる公開処理専用**。社員一覧を一時的に参照して表示名を解決した直後に、必要最小限のデータだけを返す。従業員配信用には同モジュールや元データを含めない。
3. `projectEmployeeScheduleWeek` は未確定週を必ず `null` とし、現在の確定済み週の `week.days` を投影する。確定後に管理者が修正したシフトも反映対象。
4. 配信データの許可リスト: `format`、`storeName`、`weekStart`、7日分の `date`、`shifts`/ `training` 内の `position`・`band`・`name`（シフト名）・`start`・`end`。
5. 不許可: フルネーム、従業員番号、従業員ID、誕生日、入社日、退職日、所属情報、従業員一覧、管理者の認証情報、管理備考、確認履歴、自由入力の業務文言。シフト名とフルネームが一致する場合は「従業員」に置換。
6. シフト名そのものが個人識別情報になり得る。管理者が従業員向けの表示名を事前に確認し、フルネームや機微情報を入れない。文字列だけで完全な判定はできないため、公開前の確認を必須とする。
7. 店舗別アクセスは画面の切替ボタンの非表示だけでなく、**共通パスワード照合後にサーバーが発行した閲覧セッションと店舗の対応をサーバー側で検査**。URL、クエリ、APIを改変しても他店舗のシフトを読めないようにする。
8. 閲覧者にはデータ変更権限なし。未認証者は拒否。退職者個人の権限停止は共通パスワードではできないため、退職等の際はパスワード変更と全セッションの失効を必須とする。ページやAPIレスポンスは必要最小限の構成とし、個人別の管理情報は保管しない。

## ログイン方法・パスワードの設定（決定仕様：数字6桁）
- **店舗ごとに1つの共通パスワード**を使用し、従業員番号・個人別アカウント・メール認証は使用しない。「自分のシフト」ページは作らない。
- **現在の管理者用シフト表アプリの「設定」→「従業員用シフト閲覧」**から、選択中の店舗の閲覧パスワードを設定・変更できるようにする。店舗を切り替えると別店舗の設定を表示する。他店への誤設定を防ぐため保存時に店舗名を確認する。
- 従業員はバックルーム（従業員専用区画）に掲示した **QRコード（専用URL）と共通パスワード**で閲覧する。売場・一般来客が見える場所への掲示は禁止。QRコードにはパスワードを埋め込まない。
- パスワードの作成・変更は**管理者のサーバー側認証と管理者権限の確認**を必須にする。設定画面を開けるだけで変更可能にしてはいけない。管理者用のSupabase同期パスワードとも別の秘密とする。
- パスワードは管理者/従業員のブラウザの localStorage、公開JS/HTML、Git、GitHub Pages、通常のシフトバックアップや同期データに保存しない。サーバー側でソルト付きの遅いパスワードハッシュで検証し、画面へ平文の保存値を返さない。
- **店舗ごとに数字6桁の共通パスワード（PIN）**を設定する。`000000`、`123456` などの単純な番号は登録禁止。ログインはHTTPS必須。**連続5回の誤入力後は15分間制限**し、認証API側で店舗とアクセス元を考慮した試行制限・監視を行う（他の従業員を一斉に締め出す運用障害にも注意）。これはサーバー側で実装・実証する必要があり、画面側の制限だけでは不十分。
- パスワード照合に成功した場合、**店舗に紐付く短命な閲覧専用セッション**を発行し、毎回サーバー側で店舗・権限・セッション世代を検証する。クライアントが任意の店舗IDに変更しても他店舗のデータを返さない。
- パスワードを変更すると旧パスワードと**発行済み全セッションを無効化**する。退職者がパスワードを知っている可能性があるため、退職や掲示内容の流出時には直ちに変更・掲示を差し替える。
- この方式では退職者を個別に無効化できず、在籍者同士で誰がアクセスしたかの本人特定もできない。掲示物の写真やパスワード転送による漏えいリスクは残る。リスクを受け入れられない状況では公開しない。
- 検証ブランチで実装と模擬テストを進行中。独立した配備先での確認が終わるまでは**従業員に公開しない**。

### 公開の方式と注意
- 従業員サイトは管理者の `https://kazutake1.github.io` と異なるオリジンを必須とする。同一オリジンのサブフォルダ公開は禁止。

## 運用上の注意
従業員サイトで公開するシフト名・勤務日時も、従業員間で互いの勤務状況を知る情報となる。閲覧可能者と表示範囲を店舗内で明示する。URLや画面写真の転送による二次共有は技術だけでは防げない。

### アクセス元別のPIN試行制限（検証用）

公開前は `VIEWER_VERIFIED_IP_HEADER` を設定しない。初期状態では送信元ヘッダーを参照せず、店舗内のアクセスは共有の5回制限を使う。これは未検証の経路に対する保守的な動作で、誤入力が重なると同じ店舗の全員が一時的にログインできなくなる。

アクセス元別の制限を有効にするには、実際の配信経路ですべてのリクエストの `CF-Connecting-IP` を信頼できる入口が設定すること、入口を経由しない直接到達経路がないことを、独立した架空データ環境で先に確認する。確認後にのみ `VIEWER_VERIFIED_IP_HEADER=cf-connecting-ip` を使用する。その場合も店舗全体の20回制限は残る。模擬テストの合格だけでこの設定を本番に入れない。

配備先での受け入れ確認は、架空のA店・B店と検証用端末だけで行う。入口の設定と経路を確認した後、以下の期待結果を記録する。

| 確認する操作 | 期待結果 |
|---|---|
| A店で同じIPから5回誤入力した後、別端末が同じIPで正しいPINを入力 | A店の新規ログインはそのIPで15分間制限 |
| A店へ別IP（携帯回線など）から正しいPINを入力 | 店舗全体の上限に達していなければログインできる |
| B店へ制限中のIPから正しいPINを入力 | B店の上限に達していなければログインできる |
| 制限が切れた後にA店へ元のIPから正しいPINを入力 | 再びログインできる |

Wi-Fiを共有していても端末ごとに異なるIPv6アドレスが見えることがある。判定の単位は人やWi-Fi名ではなく、信頼済みの入口が渡すIPアドレス。記録には実IP・PIN・セッショントークンを残さない。

### 閲覧データを管理者データから分離する設計案

`backend/published-week-schema-draft.sql` は、公開可能なシフト表の写しだけを非公開スキーマに保管する検証用SQL。専用の読み取り権限でこの写しだけを参照し、管理者の台帳・管理者一覧・認証情報は参照しない。一時PostgreSQLには架空の台帳とシフト表を用意し、同じ読み取り権限で写しを取得でき、台帳の読み取りが権限エラーになることを確認する。

Edge APIの草案は下記の専用接続を使用するが、配備前に、管理者が公開・更新・取り下げを行う処理、セッションから店舗を特定する処理、専用権限での配備を追加し、他店の写しをAPIが返さないことを確認する。最後に `backend/session-scoped-read-draft.sql` を適用して、読み取りロールのテーブル直接参照を取り消す。これにより、同ロールが実行できるのは有効な閲覧セッションに紐づく店舗の指定週を返す処理だけになる。SQL草案を本番に適用しない。

公開用の写しには、管理側で保存が成功した時点の同期番号を記録する。同じ店舗・週には新しい番号だけを反映し、取り下げ時も番号を残す。これにより、通信が遅れた古い更新で取り下げ済みのシフトが再表示されるのを防ぐ。公開前には、クラウド同期番号をリセットする運用も別途確認する。

閲覧APIの草案は `VIEWER_WEEK_READER_DB_URL` の専用接続へ切り替えた。DBの実行ロールが `shift_viewer_week_reader` である場合のみ、セッションの照合値と指定週を渡せる。店舗はデータベースが有効なセッションから判定し、読み取りロールは写しを直接参照できない。写しが未作成・取り下げ済みなら表示しない。旧来の管理者同期データへの読み取りには戻らない。接続先が未設定・異常ならエラーとする。

閲覧APIのPIN・セッション確認は `VIEWER_AUTH_DB_URL` の専用ロール `shift_viewer_auth` を使う。管理者一覧は所属確認用のID列だけを参照でき、管理者シフトの元データ・台帳・公開用の写し・認証アカウント情報へは接続権限を与えない。写しは別の読み取り権限で取得する。専用ロールの実配備と、配備先で閲覧関数に不要な広い資格情報を持たせない構成の確認は未実施。DB草案を本番に適用せず、現在のEdge Functionは配備しない。

管理者API草案に `syncPublishedWeek` 操作を追加した。管理者として認証された依頼を受け、保存済みの店舗データから指定週の公開用の写しを作る。週が未確定・削除済みならその写しを取り下げる。クライアントは店舗・週だけを指定し、写しの内容や同期番号は決められない。書き込み接続 `VIEWER_WEEK_PUBLISHER_DB_URL` は専用ロールのみを使う。

管理画面の草案では、サーバーが `VIEWER_AUTO_PUBLISH_ENABLED=true` と書き込み接続の設定を確認し、対象店舗のPINが設定済みと返した場合だけ、クラウド保存成功後に変更週の写しを更新する。失敗分は店舗ID・週・再試行用の印だけを同じ端末に保存し、画面を閉じても、同じ管理者アカウントで設定の「従業員用シフト閲覧」から再試行できる。店舗削除・公開停止時の検証用処理は下記のとおり。公開判定を満たすまでサーバーの自動反映を有効にしない。

閲覧停止は店舗のPIN設定を解除する。既存のQRコード・ログインを無効にし、公開用の写しも同時に削除する。再開時は新しいPINを設定し、新しいQRコードに差し替える。管理者のクラウド同期から店舗が削除された場合も同様に失効させる。開いたままの画面ですでに表示されている内容は、次の取得まで端末上に残り得る。これらは検証用SQLとコードであり未配備。

### 配備先の分離（公開前の必須条件）

Supabaseのホスト型Edge Functionsには、実行先プロジェクトの広い鍵が環境変数として渡る。コードでその鍵を使わなくても、管理者と閲覧を同じプロジェクトで実行する構成は採用しない。閲覧関数には閲覧側専用の実行先を用意し、管理者プロジェクトのURLを `VIEWER_MANAGER_PROJECT_URL` に設定する。実行先と一致する場合や既存管理者プロジェクトの場合、公開用写しの書き込み接続が置かれている場合は、閲覧APIが処理を拒否する。

ブラウザ配信用ビルドは `VIEWER_ACCESS_ORIGIN` に閲覧専用プロジェクトのHTTPSオリジンを指定する。未指定なら外部につながらないテスト用の宛先を使う。既存の管理者プロジェクトはビルド時にも拒否する。専用の実行先に管理者プロジェクトの広い鍵や書き込み接続を持ち込まない。

配備検証は架空データだけを使い、本番と独立した環境で行う。管理者プロジェクトへの読取権限が渡らないこと、信頼できるIP情報が実際に届くこと、ログイン・失効・店舗間分離を配備先に対してPCから確認するまで公開しない。スマホ実機は必須としない。無料の独立環境を確保できない場合は、模擬検証までで止め、公開は保留する。

### スマホ実機でのローカルデモ（追加料金なし）

PCとスマホを同じ信頼できるWi-Fiにつなぎ、PCのリポジトリで `node scripts/preview-employee-viewer-lan.mjs <PCのWi-FiのIPv4アドレス>` を実行する。スマホでターミナルに表示されたURLを開き、架空のA店・B店を試す。PCだけで試す場合は引数を省略できる。終了は Ctrl+C。通常の配信用ビルドには含まれず、本番通信・実データ・永続保存は使用しない。

端末の画面表示、PIN入力、店舗ごとのシフト表示、ログアウトを実機で確認できる。LAN上の接続元を使用するため、クラウドの入口がIPを正しく判定することや、配備先での権限分離を確認する試験ではない。インターネットへの公開・ポート転送は行わない。

### PCで行う配備先の確認

独立した無料の検証先に架空のA店・B店を用意して実施する。本番環境と実在する従業員のデータ・PIN・資格情報は使用しない。

| 確認 | 合格条件 |
|---|---|
| 実行環境と権限の分離 | 閲覧側に管理者用の広い鍵や書き込み権限が渡らず、閲覧用ロールから管理者データと従業員台帳を読めない |
| 店舗と表示項目の分離 | A店・B店のログインでそれぞれの作成済み公開用シフト表だけを取得でき、台帳項目は応答に含まれない |
| IP判定と試行制限 | 信頼できる入口がIPを判定することを実際の配備先で確認する。同じIPでの連続誤入力は15分間制限され、別の回線からは店舗全体の上限に達していない限りログインできる |
| 閲覧の失効 | ログアウト・PIN変更・閲覧停止に応じて旧セッションが失効し、閲覧停止後は既存のQRコードからもログインできない |

スマホ幅での画面操作はChromium・WebKitの自動テストを使う。上記の配備先の結果は自動テストの結果と区別して記録する。独立レビューと管理者の了承がそろうまで、本番に配備・公開しない。

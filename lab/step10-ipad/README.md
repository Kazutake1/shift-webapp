# STEP 10 — iPad Safari 実機検証（架空データ専用）

**本番のシフト表作成アプリではありません。** GitHubのmain、本番のstate-manager.js、従業員台帳、印刷、Supabaseには一切接続しません。

## 必須の安全条件

- kazutake1.github.io の配下に配置しない。同一オリジンの他アプリと保存領域を共有しないよう、独立したCloudflare Pagesの新規 *.pages.dev サイトを使う。
- 実際の氏名・店舗情報・勤務データ・ログイン用パスワード・既存バックアップは絶対に入力しない。
- アップロードするのはこのフォルダ内の8ファイル（index.html、app.js、vault.js、style.css、sw.js、manifest.webmanifest、icon.svg、_headers）だけ。アップロード先のルートにindex.htmlを配置する。
- リポジトリ全体、.env、APIキー、supabase-config.js、本番版のindex.html、テストログを一緒にアップロードしない。
- テスト用URLは公開Webサイトになり得る。架空データ専用であっても個人情報を持ち込まない。
- _headers のCSP・noindexが適用されることと、外部APIへの通信がないことをできる限り確認する。

## iPad操作手順

1. Cloudflare Pagesで新規Direct Uploadプロジェクトを作成。本番アプリとは別の独立した pages.dev ドメインを用意する。このフォルダの8ファイルだけをアップロードする。
2. iPadのSafariで専用URLを開く。「STEP 10」「架空データ専用」の表示を確認。
3. 本番で使っていない12文字以上の試験専用パスフレーズを入力し、架空データを初期化する。
4. 同じパスフレーズで解除し、氏名が「架空従業員A」であることを確認する。
5. 架空シフトを変更・保存する。版数が増え、模擬同期待ちと表示されることを確認する。
6. 保存失敗・競合・改ざん・平文保存の各テストを実行。合格表示を確認する。
7. 試験用暗号化バックアップを作成し、同じファイルを選択して復元する。元データの保持と版数の更新を確認する。
8. ロックして情報を隠す。架空の氏名と勤務が消え、誤ったパスフレーズでは復号できないことを確認する。
9. Wi-Fi接続中にSafariの「ホーム画面に追加」で試験用アプリを追加し、ホーム画面から起動する。
10. 機内モードでWi-Fiもオフにし、試験用アプリを閉じて再起動する。試験用パスフレーズで解除し、架空シフトと版数が維持されていることを確認する。オフライン保存も試す。
11. 通信を戻す。必要に応じて専用の架空データ削除ボタンを押す。SafariのWebサイトデータ一括消去は実行しない。

## 注意事項

- Cloudflare Pages Direct Uploadは、フォルダまたはZIPのドラッグアンドドロップでサイトを公開できる。ただしDirect Uploadプロジェクトは後からGit連携へ切り替えられない。
- クラウド同期は実装していない。模擬同期待ちの記録だけを端末内に残す。
- Service Workerは独立した検証サイトだけをキャッシュする。Safariのオフライン再起動が必ず成功する保証はない。
- 削除ボタンの対象は専用IndexedDB「shift-step10-fake-vault-20261025」だけ。localStorageや他のIndexedDBには触らない。
- 保存容量上限、電源断、OSによるデータ消去など、現段階で未検証の事項は合格と判断しない。
- 端末機種、iPadOS、Safariとホーム画面の起動方法、オンライン/オフライン状態、表示結果を記録する。共有する画像に実際の個人情報を含めない。
